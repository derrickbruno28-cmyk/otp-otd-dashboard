# Route Performance Tracker — Build Spec

Asset Operations OTP/OTD system for AJG Transport / Gomez Haulers.
Customers: AeroNet, Source One, USPS, Milwaukee Tool. Backend: Firebase.
Status: spec approved for build.

Sources: the OTD example sheet (line-item schema) and the Week 33 OTP/OTD Operations
Audit (what actually gets measured, and how misses get attributed).

---

## 1. What this app is for

Two jobs, and the second one is the reason the first one matters.

1. **Capture.** Ops logs the actual pickup and delivery events against the scheduled
   appointments, per load, with a reason on every miss.
2. **Account.** The system produces the weekly OTP/OTD audit — scorecard against target,
   fail-reason ranking, driver flagging, escalation — without anyone rebuilding it by hand.

Today step 2 is manual. The uploaded audit is titled Week 34 in its filename and Week 33
throughout its body; that is exactly the drift hand-assembly produces, and it is one of the
things generating the report from the data fixes.

### What the audit says

| | On-time | Late | Rate | Target | Gap |
|---|---|---|---|---|---|
| OTP | 118 | 26 | 81.9% | 97.0% | −15.1 pts |
| OTD | 74 | 70 | 51.4% | 95.0% | −43.6 pts |

**31 of the 70 OTD misses — 44% — are a single reason: `Driver – Made Multiple Stops`.**
Nothing else is close; the next reason is 7. Clear that one behavior and OTD goes from
51.4% to 72.9% on the same 144 loads. Every screen and report in this build is designed so
that fact is visible in week one rather than after someone spends a day in a spreadsheet.

## 2. Decisions locked

| Decision | Choice |
|---|---|
| Backend | Firebase — Firestore, Auth, Functions, Hosting, Storage |
| Existing Postgres/Render app | Retired after cutover; fresh build |
| **Stops** | Multi-stop supported; normal load is one pickup + one delivery |
| **Appointments** | Straight times; a window-close field exists per stop and stays empty |
| **LS Number** | **One per load**, not per stop — matches the audit, where a single LS# is quoted on both the OTP and the OTD side |
| **Load / Reference numbers** | Separate adjacent columns |
| **Targets** | **Per customer, fleet default OTP 97% / OTD 95%** |
| **CF / Non-CF coding** | Per metric, with a pending queue and a challenge state — **USPS only** |
| **Fail reasons** | Managed taxonomy; **multiple reasons per metric per load**, each with a note |
| **Drivers** | Tracked per individual, paired into teams per load |
| **The weekly audit** | Generated by the app: scorecard, WoW, fail-reason index, driver flagging, MTD worst performers |
| OTP graded on | Arrival at the shipper vs pickup appointment |
| Grace window | Per customer, default 15 min |
| Blank actuals | PENDING — excluded from the percentage, counted separately |
| Tender autofill | Drag-and-drop PDF; **PDF retained by default** (§9) |
| Service Type column | Dropped |

## 3. Data model

### 3.1 Load

`Filled by`: **T** tender autofill · **M** manual · **C** computed server-side.

| Field | Type | Filled by |
|---|---|---|
| `lsNumber` | string — **load stop number, one per load**; the identifier every report quotes | M |
| `loadNumber` | string — the load number (sheet's "Order Number"); dedupe key | T |
| `referenceNumber` | string — reference / pickup number, column immediately right of load number | T/M |
| `customerId` | enum: aeronet / source-one / usps / milwaukee-tool | T/M |
| `equipmentType` | enum | T |
| `status` | Tendered / Dispatched / At Shipper / In Transit / At Consignee / Delivered / Cancelled | M |
| `pieces`, `weightLbs`, `billingMiles`, `commodity` | freight facts; parse `"8250.000lbs"` to `8250` | T |
| `stops[]` | array of Stop, min 2 | T/M |
| `primaryDriverId`, `secondaryDriverId` | driver refs — the team on this load | M |
| `truckNumber`, `runType`, `tripNumber` | optional asset fields | M |
| `isShuttleLeg` | boolean — excluded from the CF breakdown, still scored on the metric earned | M |
| `otp`, `otd` | `{ status, varianceMin, deadline, reasons[] }` | C + M |
| `cf` | `{ otp, otd }` — `CF` / `NON_CF` / `CF_CHALLENGE` / `null`; **USPS only** | M |
| `weekNumber`, `weekYear`, `monthKey` | derived from the first pickup appointment | C |
| `stopOnTimePct`, `transitMin`, `firstPickupAppt`, `finalDeliveryAppt` | rollups | C |
| `createdBy`, `updatedBy`, `batchId`, `tenderId` | provenance | C |

### 3.2 Stop

| Field | Type | Filled by |
|---|---|---|
| `seq` | integer, 1-based | T/M |
| `type` | `PICKUP` \| `DELIVERY` | T/M |
| `locationName`, `address`, `city`, `state`, `zip` | zip stays a **string** — leading zeros | T |
| `appt` | timestamp | T |
| `apptEnd` | timestamp — window close; normally empty | T/M |
| `actualArrival` | timestamp — **grades this stop** | M |
| `actualDeparture` | timestamp — drives dwell | M |
| `onTime` | `{ status, varianceMin, deadline }` | C |
| `dwellMin` | number | C |

> **Naming trap, and it matters.** A load's `stops[]` are its *scheduled route stops*. The
> fail reason `Driver – Made Multiple Stops` means *unauthorized stops made en route*. These
> are unrelated concepts that share a word, and conflating them would let a legitimate
> five-stop route look like a driver behavior problem. Never derive one from the other.

### 3.3 Fail reasons

A miss carries **one or more reasons**, each with a free-text note. The audit proves this is
required: LS# 20322 carries both `Mechanical – Tire Failure En Route` and
`Driver – Made Multiple Stops` on the same OTD miss.

```
otp.reasons = [ { reasonCode, note, enteredBy, enteredAt }, ... ]
otd.reasons = [ { reasonCode, note, enteredBy, enteredAt }, ... ]
```

`failReasons/{code}` — admin-managed, seeded from the audit:

| Field | Notes |
|---|---|
| `label` | e.g. `Driver – Made Multiple Stops` |
| `category` | `DRIVER` / `SHIPPER` / `DISPATCH` / `BROKERAGE` / `MECHANICAL` / `EXTERNAL` / `PLANNING` / `COMPLIANCE` |
| `appliesTo` | `OTP` / `OTD` / `BOTH` |
| `isDriverFault` | derived: `category === "DRIVER"` — this is the audit's gold/bold rule, and it drives coaching flags |
| `active`, `sortOrder` | |

Seed set (34 reasons, verbatim from the audit):

- **DRIVER** — Made Multiple Stops · Not Utilizing Drive Time · Extended Fuel Stop Delay ·
  Late Pickup Cascaded to Delivery · Late Yard Arrival · HOS Violation / Out of Hours ·
  Unreachable / Phone Off · Call Out Due to Family Emergency ·
  Failed to Utilize DH Properly to Make OTP · Incorrect Route · Accident / Incident En Route ·
  Shuttle Delay
- **SHIPPER** — Freight Not Ready · Loading Error · Late Departure at Shipper - No Late Slip
  Given · Detention Exceeding Appointment Window · Held at Shipper / Cascaded to Late Delivery
- **DISPATCH** — Late Load Assignment · Late Roll Out from Yard · Recovery
- **BROKERAGE** — Approved to be Late Due to Previous Load Delivery · Load Recovery ·
  Late Tender from Broker
- **MECHANICAL** — Tire Failure En Route · Trailer Issues · Air System Failure / Low Air
  Pressure · Repairs En Route · Trailer Lights Not Working · Due to DOT Regulations · See Notes
- **EXTERNAL** — Traffic / Accident Delay · Weather / Road Conditions
- **PLANNING** — Not Enough Transit Time
- **COMPLIANCE** — DOT Regulated Break

**Cascade assist.** When OTP is LATE and OTD is LATE on the same load, the reason picker
offers `Driver – Late Pickup Cascaded to Delivery` first. It is offered, never auto-applied —
7 loads in Week 33 were genuine cascades and the rest were not.

### 3.4 Driver

| Field | Notes |
|---|---|
| `name`, `active` | |
| `allTime` | `{ loads, otpOnTime, otpLate, otdOnTime, otdLate, otpPct, otdPct }` — **per individual**, across every week and every team pairing |
| `reviewState` | `NONE` / `STEP_1_CALL` / `STEP_2_WRITE_UP` |
| `reviewedBy`, `reviewedAt`, `reviewNotes` | |

Teams are a per-load pairing (`primaryDriverId` + `secondaryDriverId`), not a fixed entity —
the audit shows the same driver in different pairings across weeks, and all-time percentages
are computed for the individual.

### 3.5 Customer

| Field | Default |
|---|---|
| `name`, `aliases[]`, `active` | |
| `targets` | `{ otp: 0.97, otd: 0.95 }` — editable per customer; unset inherits the fleet default |
| `graceMinutes` | `{ pickup: 15, delivery: 15 }` |
| `earlyToleranceHours`, `earlyCountsAsMiss` | `2`, `false` |
| `cfCodingEnabled` | **`true` for USPS only**, `false` for the other three |

`settings/fleet` holds the fleet-wide default targets (97% / 95%) and the week definition.

## 4. Scoring

### 4.1 Per stop

```
grace     = customer.graceMinutes[stop.type]        (default 15)
deadline  = (stop.apptEnd ?? stop.appt) + grace

stop.onTime =
  PENDING   if appt or actualArrival is missing
  EARLY     if actualArrival < appt - customer.earlyToleranceHours
  ON_TIME   if actualArrival <= deadline
  LATE      otherwise
```

### 4.2 Per load

```
otp  = first stop where type == PICKUP    (by seq)
otd  = final stop where type == DELIVERY  (by seq)
stopOnTimePct = on-time stops / graded stops        (every stop, not just the bookends)
```

### 4.3 Rates, targets, gap

```
OTP%  = ON_TIME / (ON_TIME + LATE + EARLY-if-counted)
target = customer.targets.otp ?? fleet.targets.otp
gap    = (rate - target) in percentage POINTS, one decimal, signed
```

Every scorecard renders **Rate · Target · Gap**, exactly as the audit does. Filtered to one
customer it uses that customer's target; fleet-wide it uses the fleet default.

`PENDING` loads are **excluded from the denominator and displayed as their own count beside
every percentage.** No percentage renders anywhere without its pending count. Your current
sheet's `LET()` formula returns `FALSE` on a blank actual, which counts unkeyed loads as
misses and understates every customer.

### 4.4 Weeks

Weeks run **Sunday–Saturday** (Week 33 = Aug 9–15, 2026, which is Sun–Sat). Configurable in
`settings/fleet`. A load belongs to the week of its **first pickup appointment**. Note this
is *not* ISO week numbering — ISO calls Aug 9–15 2026 week 33 only if weeks start Monday, so
the app stores its own `weekNumber` rather than deriving one from a date library default.

### 4.5 CF / Non-CF — USPS only

Applies only where `customer.cfCodingEnabled` is true. **Per metric**, not per load: OTP and
OTD each get their own determination, because the audit breaks them out separately.

- `CF` — contractor failure
- `NON_CF` — not contractor failure
- `CF_CHALLENGE` — determination under challenge
- `null` — **not yet coded**. This is a to-do, not a verdict. Uncoded late loads appear in a
  **Needs CF Coding** queue with a count badge, and the audit renders them as `No Flag` with
  the standing note that no determination has been entered.

Loads with `isShuttleLeg` are excluded from the CF breakdown and still scored on the metric
earned.

## 5. Screens

### 5.1 Loads

All four customers on one page. Filtering is a chip row, not a page change. Filters:
customer, week / date range, status, OTP and OTD outcome, reason, reason category, CF state,
driver, and `Needs CF coding` / `Missing reason` / `Pending actuals` quick filters. Search
across LS # / load # / reference # / city / consignee / driver.

- **Load view** — one row per load: LS#, load #, reference #, customer, lane, appointment vs
  actual for pickup and delivery, OTP and OTD chips, reason chips, CF chip (USPS), driver
  team, stop-count badge. Row expands to the stop list.
- **Stop view** — one row per stop. This is how ops keys actuals and it is the surface that
  has to be fastest. Inline edit on `actualArrival` / `actualDeparture` in both views: two
  clicks, tab between fields, Enter saves, Esc cancels.
- **Reason entry** — clicking a LATE chip opens the reason picker inline: search the
  taxonomy, add more than one, note per reason. A LATE load with no reason is visibly
  incomplete and counts into a **Missing reason** badge.

### 5.2 Scorecards

KPI strip: Loads scored · OTP Rate/Target/Gap · OTD Rate/Target/Gap · All-Stop % · Pending ·
Avg minutes late. Recomputes with the active filter. Per-customer cards below, each against
its own target. Week-over-week block: rate, late count, total scored, with deltas.

### 5.3 Weekly Audit

Generates the audit document from the data, for any week, fleet-wide or filtered to one
customer — which is new: the current audit is fleet-wide only, and per-customer OTP/OTD is
the thing this build adds. Sections mirror the existing report:

1. **Scorecard** — on-time, late, rate, target, gap; WoW comparison; CF breakdown (USPS)
   with the No Flag note.
2. **Top fail reasons** — ranked with ties sharing a rank, overflow reasons listed inline
   with counts, split OTP and OTD.
3. **Drivers flagged for review** — every driver or team with **3 or more fail reasons
   (OTP + OTD combined)** that week, ranked by fail count. Two independent boxes per driver,
   OTP fails and OTD fails, listing only the failing LS#s. All-time individual OTP/OTD shown.
   Reasons in the `DRIVER` category are visually flagged for coaching review.
4. **Top 10 worst performers, month to date** — minimum 3 loads, ranked by total late events
   (OTP fails + OTD fails), with monitoring state.
5. **Fail reason summary index** — every LS# grouped by reason, with driver names.

Export as a shareable page and as PDF. Regenerating a week reruns from current data, so
late-entered reasons flow through.

### 5.4 Driver Performance

Per-driver page: all-time OTP/OTD, loads, fail history by reason, week-by-week trend,
review state. **Escalation is tracked, not just displayed:** a driver flagged in consecutive
weeks moves `STEP_1_CALL` → `STEP_2_WRITE_UP` per SOP GHL-OPS-003, with reviewer and
timestamp recorded. The app proposes the escalation and a human confirms it — a write-up is
a personnel action and should never fire automatically.

### 5.5 Everything else

- **Add Load** — drawer; opens with one pickup and one delivery; Add stop appends more.
- **Tender drop zone** — §9.
- **Excel/CSV import** — the column mapper from `public/index.html`, remapped. A flat sheet
  row becomes a load with two stops. Batch ID + undo.
- **Admin** — customers and targets, fail-reason taxonomy, drivers, fleet settings, users.
- **Reports** — CSV of the filtered view, sheet-compatible or one-row-per-stop.
- **Audit trail** — who set each actual, reason, and CF code, and when. These numbers go to
  customers and into personnel files; they need provenance.

## 6. Firebase architecture

**Stack:** Vite + React + TypeScript + Tailwind on Firebase Hosting.

| Collection | Contents |
|---|---|
| `loads/{id}` | §3.1, with `stops[]` embedded |
| `customers/{id}` | §3.5 |
| `drivers/{id}` | §3.4 |
| `failReasons/{code}` | §3.3 |
| `settings/fleet` | Default targets, week definition |
| `weeklyAudits/{year}_{week}` | Generated audit snapshots |
| `driverFlags/{year}_{week}_{driverId}` | Flag, fail count, review state, escalation history |
| `tenders/{id}` | §9 |
| `importBatches/{id}` | Undo |
| `auditLog/{id}` | Field-level change history |
| `users/{uid}` | `admin` / `ops` / `viewer` |

Stops are embedded, not a subcollection — a load is read and written as a unit. The cost is
that you cannot query across stops, which is why `otp`, `otd`, `weekNumber`, `monthKey`,
`firstPickupAppt` and `stopOnTimePct` are denormalized onto the load.

**Indexes:** `(customerId, firstPickupAppt desc)` · `(weekYear, weekNumber, customerId)` ·
`(customerId, otp.status, firstPickupAppt)` · `(monthKey, primaryDriverId)` ·
`(customerId, loadNumber)` · `(cf.otd, weekYear, weekNumber)`.

### Functions (Node 20, TypeScript, v2)

| Function | Trigger | Job |
|---|---|---|
| `onLoadWrite` | load write | Grade stops, roll up otp/otd/stopOnTimePct/transitMin, stamp week and month |
| `recalcDriverStats` | load write | Update all-time individual stats for both drivers on the load |
| `evaluateDriverFlags` | scheduled + on demand | 3+ fails in a week → flag; consecutive weeks → propose Step 2 |
| `generateWeeklyAudit` | callable | Build the audit snapshot for a week ± customer |
| `parseTender` | Storage finalize | PDF → load + ordered stops |
| `writeAudit` | load write | Field-level diff into `auditLog` |

**Every computed value is function-write-only.** Firestore rules reject client writes to
them. Someone who can type their own OTP result can type their way to 100%.

Cloud Functions and Secret Manager require the **Blaze** plan.

## 9. Tender PDF — extraction and retention

Cloud Function, Anthropic TypeScript SDK, model **`claude-opus-5`**. The PDF goes straight
through as a base64 `document` block — no separate OCR step — with the response constrained
by `output_config.format` against a JSON Schema matching §3.

```ts
const res = await client.messages.create({
  model: "claude-opus-5",
  max_tokens: 16000,
  thinking: { type: "adaptive" },
  output_config: { format: { type: "json_schema", schema: TENDER_SCHEMA } },
  messages: [{ role: "user", content: [
    { type: "document", source: { type: "base64", media_type: "application/pdf", data: b64 } },
    { type: "text", text: EXTRACTION_PROMPT },
  ]}],
});
```

**Retention: keep the PDF, with a switch to turn it off.** `settings/fleet.retainTenderPdf`
defaults to `true`; the file lives in Cloud Storage at `tenders/{customerId}/{tenderId}.pdf`
and opens from the load. The reason to keep it is disputes — when a customer says the
appointment was 0800 and your record says 1000, the tender is the evidence, and a stripped
record is your word against theirs. Cost is not a factor: at roughly 200KB a tender and
~144 loads a week, a full year is about 1.5GB, or a few cents a month.

With the switch off, `parseTender` extracts, writes `parsedFields`, and deletes the file,
keeping a SHA-256 fingerprint and the filename so a re-upload of the same document is
recognized. An optional `tenderRetentionDays` purges files older than N days either way.

Extraction rules:

- `stops` is an **array in printed order** — a four-stop tender produces four stops.
- Load number and reference number are **separate schema fields**. Tenders label them
  inconsistently (Load #, Order #, Pro #, PU #, Ref #, BOL #), so the schema requires the
  model to report which label it read for each.
- Every field carries a `confidence` and verbatim `sourceText` for the review panel.
- API key from **Secret Manager**. Never in the client bundle.
- **A parsed tender never saves itself** — it lands in a review panel, badged, until a human
  confirms. A misparsed appointment silently corrupts that lane's OTP forever.
- Missing field returns `null`. Never guess an appointment time.

## 10. Still open — assume and flag, do not stall

1. **Timezones.** Stop-local or all Central? Default: store the instant, derive the stop's
   zone from the ZIP, display stop-local with a toggle.
2. **Early arrivals.** Does 4 hours early count against you anywhere? Default: no.
3. **USPS shape.** Always consignee, always shipper, or both ends?
4. **Edit lock.** Who can change an actual after a load is Delivered, and does it lock after
   N days? Default: `manager` and above, no time lock, every change audited.
5. **TMS actuals.** Can the TMS export the actual columns, or were the sample ones typed?
   If it can, we import them and ops only fills gaps.
6. **Firebase project ID**, and is Blaze billing on?
7. **Reviewer.** The audit names Kevin. Default: reviewer is any user with the `manager`
   role, recorded per review, rather than a hardcoded name.
8. **Volume.** Week 33 scored 144 loads. Assume ~150/week, ~8k/year — comfortably inside
   client-side aggregation for the dashboard, with the scheduled rollups still worth having
   for the audit.
